Sentinel

A deterministic reliability harness for AI coding agents. Sentinel wraps around any LLM-powered coding tool and independently verifies that it actually did what it claims — catching hallucinated completions, sandboxing unsafe operations, and automatically recovering from failures.

What is Sentinel

Sentinel is a verification and recovery layer that sits between an AI coding agent and the real world. It ensures that when an agent says "I fixed the bug," the bug is actually fixed — by independently running the tests, inspecting the on-disk git diff, and rejecting false success claims.

Day-to-day, Sentinel does three things:

  1. Sandboxes every tool call the agent makes — file reads/writes are path-jailed to the workspace, shell commands are restricted to a strict whitelist (pytest, python3, ls, cat, grep), and environment variables containing API keys or credentials are stripped before any subprocess executes.
  2. Verifies task completion through a deterministic gate that combines real test execution (actual pytest exit code) with physical git diff analysis. The LLM's self-report is completely ignored.
  3. Recovers from failures automatically — rolling back the workspace via git, injecting diagnostic context into the agent's prompt, and retrying up to 3 times before tripping a circuit breaker.

The entire system is designed so that the parts that matter for safety — verification, sandboxing, checkpointing, recovery — are pure deterministic Python. The LLM is only involved in two places: generating a plan, and proposing tool calls. Everything else is code we control.

Key Result
Under controlled chaos fault injection, raw AI agents produce 0% task success with 100% false success claims. With Sentinel wrapping the same agent, task success rises to 100% with 0% false claims.

Why It's Needed

The Problem: AI Agents Lie About Their Work

AI coding agents (Copilot, Cursor, Aider, SWE-agent) can generate code. But they have a dangerous pattern: they report success even when they fail. This is called a hallucinated completion or false success claim.

The agent genuinely believes it solved the problem, but in reality:

  • The code it wrote has a syntax error (output was truncated mid-generation)
  • It edited the wrong file entirely
  • The tests still fail on disk
  • It didn't actually change anything at all — but said "Done!"

What Existed Before

Before Sentinel, the only options were:

  • Trust the agent — accept its self-report and manually review the output. Doesn't scale, and developers miss subtle bugs.
  • Use expensive models — pay 10–50× more for GPT-4/Claude to reduce (but not eliminate) hallucination rates.
  • Prompt engineering — ask the model "are you sure?" or add chain-of-thought reasoning. Helps marginally. Does not produce ground truth.

None of these provide deterministic proof that the task was completed. Sentinel does.

How It Works Under the Hood

Sentinel's engine is a Python state machine that drives a TaskState object through a fixed set of stages. The LLM is a component inside this loop — not the driver of it.

The State Machine

Fig 1. Sentinel orchestrator state machine. The LLM participates only in PLANNING and EXECUTING. All other transitions are deterministic Python logic.

The orchestrator (agent/orchestrator.py) drives this loop with a hard max_loop_ticks=30 safety cap. Even if the recovery logic has a bug, the loop physically cannot iterate more than 30 times.

TaskState — The Single Source of Truth

Every component reads from and writes to one dataclass. Nothing lives exclusively inside the LLM's context window: 

@dataclass
class TaskState:
    task_id: str                        # e.g. "task_001"
    workspace_path: str                 # isolated git worktree path
    instruction: str                    # "Fix the auth bug..."
    plan: list[str]                     # ["Read auth.py", "Write fix", "Run tests"]
    current_step_index: int             # which plan step we're on
    tool_call_log: list[dict]           # full history of every tool invocation
    attempt_count: int                  # retries so far (0, 1, 2)
    injected_fault: str | None          # "truncated_diff" or None
    verifier_result: dict | None        # verifier's structured verdict
    status: str                         # "planning" | "executing" | "verifying" | ...
    model_used: str                     # "local" | "frontier"
    checkpoint_id: str | None           # last saved checkpoint namecore/types.py

This is JSON-serializable via to_json() / from_json(). If the process crashes, we reload from the last checkpoint file and continue exactly where we left off.

Sandbox & Security

The agent interacts with the filesystem through exactly four tool functions. Every call passes through two security layers:

Layer 1: Path Jail

Every file path the agent provides is resolved to an absolute path and checked against the workspace root: 

def _resolve_in_workspace(path: str, workspace_path: str) -> str:
    target_real = os.path.realpath(os.path.join(workspace_path, path))
    ws_real     = os.path.realpath(workspace_path)
    if os.path.commonpath([target_real, ws_real]) != ws_real:
        raise SandboxViolation(f"Path '{path}' escapes workspace")
    return target_realsandbox/tools.py

This catches:

  • ../../etc/passwd — relative traversal
  • /root/.ssh/id_rsa — absolute paths outside workspace
  • Symlink escapes — realpath() resolves symlinks before the check

Layer 2: Command Whitelist

ALLOWED_COMMANDS = {"pytest", "python3", "ls", "cat", "grep"}sandbox/executor_sandbox.py

The first token of any shell command is checked against this set. If the agent tries rm -rf /, curl, wget, powershell, or anything else — a ToolExecutionError is raised before a single byte of the command executes.

Environment Sanitization

Before any subprocess spawns, Sentinel strips all environment variables matching sensitive prefixes: 

SENSITIVE_ENV_PREFIXES = (
    "AWS_", "GITHUB_", "OPENAI_", "ANTHROPIC_",
    "SSH_", "AZURE_", "GCP_", "GOOGLE_",
    "TOKEN", "SECRET", "KEY", "PASSWORD", "CREDENTIAL",
)sandbox/executor_sandbox.py

The agent never sees your API keys, cloud credentials, or SSH keys — even in the fallback host subprocess mode.

The Verifier Gate

This is the component that catches lying agents. The verification formula is absolute: 

passed = (test_exit_code == 0) and (not timed_out) and (diff_valid)verifier/verifier.py

All three conditions must be true:

CheckWhat it verifiesWhat it catches
test_exit_code == 0 Real pytest passes inside sandbox Agent claiming fix when tests still fail
not timed_out Tests completed within timeout Infinite loops, hanging processes
diff_valid Git diff is non-empty AND within expected file boundary Zero-change hallucinations, unauthorized file edits

The diff analyzer (verifier/diff_analyzer.py) runs git diff HEAD, filters out .pyc and __pycache__ noise, and validates that only the expected files were touched.

Chaos Engineering

Sentinel doesn't just run tasks — it deliberately breaks things to prove the recovery system works. The FailureInjector uses a fixed random.Random(seed=42) so every benchmark run produces identical faults.

Fault TypeWhat It DoesWhat It Simulates
TRUNCATED_DIFF Cuts file content to 50% before writing to disk Context window overflow / output truncation
SYNTAX_CORRUPT Prepends class _Broken(((: to the file Malformed LLM output
TOOL_TIMEOUT Replaces command with sleep 5, timeout = 1s Network/tool infrastructure failures
FLAKY_TEST Replaces command with sys.exit(1) Non-deterministic test failures

Faults are injected between the LLM's output and the sandbox — the agent proposes a correct write, but Sentinel's chaos engine corrupts it before it hits disk. This tests whether the verifier + recovery loop can catch and fix the corruption.

Recovery & Rollback

When verification fails, the RecoveryController evaluates the failure and decides:

1

ABORT_FAIL circuit breaker

If attempt_count >= max_attempts (default 3) — stop immediately. Prevents infinite retry loops and unbounded token consumption.

2

ESCALATE model switch

If on the final attempt AND using a local model — switch to a cloud/frontier model (Groq) for one last attempt with a more capable LLM.

3

REPLAN strategy change

If the error mentions "unauthorized files" or "boundary violation" — the agent's plan was wrong. Insert a diagnostic step into the plan.

4

RETRY try again

Default action: Roll back workspace (git checkout -- . + git clean -fd), restore checkpoint state, inject test failure diagnostics into the next prompt, and re-execute the plan from step 0.

The rollback is atomic: the checkpoint system saves TaskState to JSON after every step, and the git worktree revert wipes all dirty changes. The retried execution starts from a perfectly clean state.

The Role of Git & Audit History

A common question is: What exactly is Git doing in Sentinel, and can we actually connect to its internal repositories to visually see the commits and rollbacks?

In Sentinel, Git is not just version control — it is the physical filesystem isolation and transaction engine. While the LLM operates in an abstract space of prompts and tokens, Git is what anchors every action to concrete disk reality.

The 4 Core Responsibilities of Git

Git Operation Code Location Why It Is Critical
git worktree add --detach sandbox/workspace.py Zero-Copy Isolation: Creates a detached workspace pointing at the exact base_commit. The primary repository stays 100% immutable. Multiple tasks run simultaneously on the same host without cloning or disk bloat.
git add -N . verifier/diff_analyzer.py Untracked File Indexing: When an agent creates a new file, standard git diff ignores it! git add -N (intent-to-add) indexes untracked files into Git without staging their contents, making new files instantly visible to the diff engine.
git diff <base_commit> verifier/diff_analyzer.py Ground-Truth Verification: Extracts the exact modifications made by the agent. Analyzes insertions, deletions, modified files, and enforces file boundary rules (e.g. rejecting edits to unauthorized files or tests).
git checkout -- . + clean -fd core/checkpoint.py Physical Rollback: When verification fails, this wipes all corrupted code, truncated files, and junk untracked files in milliseconds. Leaves the workspace in a pristine baseline state before retry.

TaskState Checkpoints vs. Git Commits

It is important to distinguish between the two layers of state in Sentinel:

  • TaskState JSON Snapshots (core/checkpoint.py): Stores the internal Python memory — which plan step we are on, prompt history, retry counters, model used, and verifier feedback.
  • Git Commits (git_commit_step()): Records the physical repository state on disk so that every phase of agent work leaves an immutable audit trail.

Can You Connect to Remote Repositories & Inspect Visually?

Yes, absolutely. Because each task workspace is a 100% standard Git repository created on your filesystem, you can view and interact with it in three ways:

1

Local Visual Inspection (VS Code, GitLens, or Terminal)

Every run creates an active Git directory at:
Windows: %TEMP%\sentinel-runs\<task_id>\workspace
Linux/macOS: /tmp/sentinel-runs/<task_id>/workspace

You can open that folder directly in VS Code or any visual Git tool (GitLens, Sublime Merge, Sourcetree). You can immediately see the graph of commits, open each commit to see the red/green side-by-side diff, inspect the corrupted file from attempt 0, and view the clean fix from attempt 1.

2

Pushing Internal Task Repos to Remote GitHub / GitLab

You can connect Sentinel's internal repository to any remote GitHub repository with a single remote push hook: 

# Add remote and push the task's execution branch to GitHub
git -C /tmp/sentinel-runs/task_01/workspace remote add origin git@github.com:your-org/sentinel-runs.git
git -C /tmp/sentinel-runs/task_01/workspace push -u origin HEAD:run-task-01-audit

On GitHub, you can navigate to the branch run-task-01-audit, click Commits, and visually browse the exact historical timeline of the agent's work, including the failure and automated rollback!

3

Embedded Web Dashboard Diff & History API

Sentinel's server provides the GET /api/runs/{id}/diff endpoint and get_git_history() helper. This allows the frontend dashboard to display an interactive, visual Git commit tree and syntax-highlighted diff viewer directly in the browser without leaving the UI.

Data Flow: A Complete Execution

Tracing a task with TRUNCATED_DIFF fault injection through the entire system:

1

Task arrives

POST /api/runs with {"task_id": "task_001", "model": "llama3.1:8b", "fault_type": "truncated_diff"}. The server creates a TaskState with status: "planning" and spawns a background worker.

2

Workspace isolation

workspace.py creates a detached git worktree. The base repo is now immutable — all edits happen in the isolated copy.

3

Planning

The orchestrator calls planner.py → the LLM returns ["Read auth.py", "Write the fix", "Run tests"]. Checkpoint saved.

4

Executing (Step 1: Write)

The executor prompts the LLM → it returns {"tool": "write_file", "args": {"path": "auth.py", "content": "...correct fix..."}}.

🔴 CHAOS INJECTION: The FailureInjector truncates the content to 50% before tools.py writes it to disk. The file on disk is now broken.

5

Verifying

verifier.py runs pytest in the sandbox → exit code 1 (tests fail on truncated code). Diff is valid (file was changed). Verdict: FAILED (test didn't pass).

6

Recovering

RecoveryController evaluates: attempt_count=0, error mentions "exit code" → RETRY.
Rollback: git checkout -- . + git clean -fd wipes the truncated file. State reloaded from checkpoint. The fault is already consumed (injected_fault = None) so it won't fire again.

7

Executing (Retry — Clean)

Same plan re-executes. This time no fault → LLM writes the correct fix → tests pass → verifier.py returns passed: True → status: "done" ✅
